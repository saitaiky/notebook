A programming paradigm is a recurring way to organise computation and state. Paradigms are design tools, not exclusive
language categories: Python, JavaScript, Java, C#, and many other languages support more than one.

The useful question is not "which paradigm wins?" It is "which model makes this problem, its state changes, and its
failure behaviour easiest to understand?"

## Imperative and declarative styles

Imperative code describes operations and control flow. Declarative code describes a desired result through an abstraction
whose implementation owns more of the control flow.

~~~javascript
// Imperative: the loop and accumulator are explicit.
function total(values) {
  let result = 0;
  for (const value of values) {
    result += value;
  }
  return result;
}

// More declarative: reduce owns the iteration.
function totalWithReduce(values) {
  return values.reduce((result, value) => result + value, 0);
}
~~~

The second example is not free of imperative execution; that execution moved behind the collection API. Declarative
interfaces can improve clarity when their contract is well understood, but they can also hide cost, ordering, retries, or
side effects. SQL is declarative, yet query plans and indexes still matter.

## Procedural programming

Procedural design groups steps into functions or procedures and composes them through explicit calls. It is effective for
algorithms, transformations, scripts, and workflows whose ordering is central.

Prefer small procedures with clear inputs, outputs, and side effects. A procedure does not need to be side-effect-only;
functions that return values are normal parts of procedural programming.

## Object-oriented programming

Object-oriented design groups behaviour with state and models collaboration through objects or interfaces.

- **Encapsulation** protects invariants behind an API.
- **Abstraction** exposes the relevant contract while hiding replaceable detail.
- **Polymorphism** lets callers depend on a role or protocol rather than one concrete implementation.
- **Inheritance** reuses or specialises behaviour, but composition often creates looser coupling.

OOP is valuable for stateful domain behaviour and substitutable components. It becomes difficult when inheritance trees
encode accidental reuse, objects expose mutable state widely, or a model copies real-world nouns without clarifying
behaviour and invariants.

## Functional programming

Functional design emphasises expressions, composition, explicit data flow, immutable values, and functions that avoid
observable side effects.

A pure function produces the same result for the same inputs and does not modify external state. Keeping a decision pure
makes it easier to test and reason about; side effects can be placed at explicit boundaries.

~~~javascript
const applyDiscount = (price, rate) => price * (1 - rate);

const updatedOrders = orders.map((order) => ({
  ...order,
  total: applyDiscount(order.total, discountRate),
}));
~~~

Real systems still perform I/O and mutate durable state. Functional techniques help isolate those effects rather than
pretending they do not exist.

## Event-driven and reactive programming

Event-driven systems respond to events such as user actions, messages, timers, and state changes. Reactive APIs propagate
changes through streams or dependency graphs.

This style decouples producers from consumers and fits asynchronous interfaces, but it makes ordering, retries,
backpressure, duplicate delivery, and tracing part of the design. Continue with
[synchronous and asynchronous communication](/software-development/system-design/sync-async/) and
[queue semantics](/software-development/system-design/sync-async/queue/overview/).

## Choose by pressure

| Pressure | Useful starting style |
| --- | --- |
| A stateful domain with strong invariants | Encapsulated objects or modules |
| A deterministic transformation pipeline | Functional composition |
| An explicit operational sequence | Procedural or imperative workflow |
| Querying a data set | Declarative query language |
| Many independent reactions to changes | Event-driven design |

Mix styles deliberately. A service can use objects for domain state, pure functions for decisions, SQL for persistence,
and events for integration. Consistency of boundaries matters more than ideological purity.
