Linux is the runtime beneath most server, container, and cloud workloads in this notebook. This section is organised around
the questions an engineer faces in production: what is running, what can it access, where is its state, how does traffic
reach it, how is it supervised, and what evidence explains a failure?

## Learning path

| Stage | Read | Outcome |
| --- | --- | --- |
| Work at the command line | [Bash introduction](/linux/bash-intro/) → [practical Bash](/linux/bash-practical/) | Understand shell startup, quoting, redirection, pipes, exit status, and safe composition. |
| Understand state and identity | [Filesystems](/linux/file-system/) → [POSIX users](/linux/posix-user/) → [permissions and special bits](/linux/uid-gid-stickbit/) | Explain paths, mounts, ownership, permissions, and persistence. |
| Understand program execution | [Kernel and userspace](/linux/kernel-userspace-system-calls/) → [processes and signals](/linux/process/) → [memory](/linux/memory/) | Follow a program from a system call through scheduling, virtual memory, and termination. |
| Understand communication | [Linux networking](/linux/networking/) | Diagnose DNS, routes, listening sockets, and failed connections layer by layer. |
| Operate long-running workloads | [Namespaces and cgroups](/linux/namespace/) → [boot](/linux/loading-sequence/) → [systemd services](/linux/services-systemd/) | Connect containers and services to the host mechanisms that start, isolate, and supervise them. |
| Maintain and diagnose hosts | [CPU architecture](/linux/cpu-architecture/) → [package management](/linux/package-manager/) → [observability](/linux/observability/) → [security](/linux/security/ssh/) | Select compatible binaries, manage trusted software, gather evidence, and secure access. |

## A production troubleshooting loop

Start with the symptom, then move down the stack without guessing:

1. Confirm the request and the failure boundary: client, DNS, network, process, dependency, or storage.
2. Inspect service state and recent logs.
3. Check resource pressure: CPU, memory, disk space, file descriptors, and connection limits.
4. Verify identity and permissions.
5. Compare the running configuration and package version with the intended state.
6. Change one thing, observe the result, and record what the evidence disproved.

The [observability page](/linux/observability/) turns this loop into a command-oriented checklist.

## How deep should an application engineer go?

You do not need to memorise every kernel subsystem. You should be able to explain the boundary between a process and the
kernel, inspect the process and network state of a host, recognise resource exhaustion, and connect a container or managed
AWS service to the Linux mechanism it abstracts. Learn a command together with the question it answers; command lists
without a diagnostic model are difficult to transfer to a new incident.

Continue with [kernel and userspace](/linux/kernel-userspace-system-calls/) for the runtime model, or return to the
[Software Development map](/software-development/) to follow a design concern from code to cloud.
