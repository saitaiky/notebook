SSH protects remote terminal sessions, command execution, and file transfer over an untrusted network. Secure operation
requires two different trust decisions:

1. The client verifies the server host key.
2. The server authenticates the user or workload.

Encryption without host verification can still connect you securely to the wrong machine.

## Host verification

The client stores trusted host keys in <code>known_hosts</code>. On first use, verify the fingerprint through a separate
trusted channel before accepting it. Treat an unexpected changed-host-key warning as an investigation, not an obstacle to
remove automatically.

For managed fleets, distribute host certificates or verified host keys instead of teaching users to accept any prompt.

## Public-key authentication

Generate a modern key and protect it with a strong passphrase for interactive use:

~~~bash
ssh-keygen -t ed25519 -a 64 -f ~/.ssh/id_ed25519
~~~

The private key remains on the client. The public key or a trusted user certificate is installed on the server. Keep
private-key permissions restrictive and never paste a private key into a ticket, chat, repository, or shell history.

Passphrase-less keys may be justified for tightly controlled automation, but they need compensating controls: limited
account privileges, constrained destinations or commands, short lifetime, secret-store protection, rotation, and
monitoring. They should not be the default example for a developer's personal key.

## SSH agent

An agent holds unlocked private keys in memory and performs signing operations for clients:

~~~bash
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
ssh-add -l
~~~

The agent reduces repeated passphrase entry; it does not copy the private key to the server. Protect access to the local
agent socket and remove keys when they are no longer needed.

## Client configuration

Use <code>~/.ssh/config</code> to make identity and destination choices explicit:

~~~sshconfig
Host production-bastion
  HostName bastion.example.com
  User operations
  IdentityFile ~/.ssh/id_ed25519
  IdentitiesOnly yes
~~~

This is safer and more reviewable than relying on whichever key the client tries first.

## Agent forwarding and jump hosts

Agent forwarding lets a remote host request signatures from your local agent. A compromised remote host can abuse that
capability while the forwarding session exists. Prefer <code>ProxyJump</code>, workload-specific credentials, or
short-lived certificates; enable agent forwarding only for a justified destination.

~~~bash
ssh -J operations@bastion.example.com app@private-host.example.com
~~~

## Server-side baseline

- Disable direct root login.
- Prefer public-key or certificate authentication.
- Restrict users, groups, networks, and commands according to purpose.
- Keep the SSH implementation patched.
- Monitor authentication failures and privileged sessions.
- Maintain a tested recovery path before changing remote-access policy.

## AWS access

Direct SSH is not always required. [Systems Manager Session Manager](/aws/management/ssm/) can provide audited access
without opening an inbound SSH port or distributing long-lived host keys. Where SSH remains appropriate, combine it with
[EC2](/aws/compute/ec2/), restrictive security groups, controlled bastions, short-lived credentials, and least-privilege
[IAM](/aws/management/iam/).
