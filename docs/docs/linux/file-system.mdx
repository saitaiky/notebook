Linux presents files through one directory tree rooted at <code>/</code>. Different filesystems are attached to that tree
at mount points. A path is therefore not a physical disk location; it is a name resolved through directory entries and the
calling process's mount namespace.

## Files, names, and inodes

On common Unix filesystems, a directory entry maps a name to an inode. The inode stores file metadata and points to file
data; the filename belongs to the directory entry.

- A **hard link** adds another directory entry for the same inode.
- A **symbolic link** stores a path to resolve later.
- Removing one hard link does not remove the underlying file while another link or open descriptor still references it.
- A process can continue using an open file after its directory entry is removed, which explains some "disk full but I
  deleted the log" incidents.

Inspect with:

~~~bash
ls -li PATH
stat PATH
readlink -f PATH
lsof +L1
~~~

## Mounts and filesystem types

~~~bash
findmnt
lsblk -f
df -h
df -i
du -xhd1 PATH
~~~

<code>df</code> reports filesystem capacity; <code>du</code> walks visible directory entries. They can disagree because
of deleted-but-open files, mount boundaries, snapshots, reserved blocks, or concurrent changes. Check both free blocks
and free inodes.

Persistent mounts are commonly described in <code>/etc/fstab</code>. Prefer stable identifiers such as UUIDs rather than
device names that may change across boots.

## Permissions are evaluated during path traversal

Access depends on the process credentials, directory traversal permissions, target mode or ACL, mount options, and
possibly a mandatory-access-control policy. A writable file is not reachable if the process cannot traverse a parent
directory. The <code>namei -l PATH</code> command is useful for viewing every path component.

Continue with [POSIX users](/linux/posix-user/) and [special permission bits](/linux/uid-gid-stickbit/).

## Local and network filesystems

ext4 and XFS are common Linux local filesystems. NFS exposes a shared filesystem over a network, changing failure and
performance assumptions: latency, server availability, identity mapping, caching, and mount behaviour now matter.

Before choosing shared files, ask:

- Must several hosts see the same POSIX namespace?
- Are concurrent writers expected?
- What consistency and locking semantics does the application require?
- What happens when the network or storage server is slow?
- Does the workload need block, file, or object semantics?

## AWS storage map

| Requirement | Starting point |
| --- | --- |
| Block device for one compute attachment pattern | [EBS](/aws/storage/ebs/) |
| Shared NFS-compatible filesystem | [EFS](/aws/storage/efs/) |
| Durable object storage and API access | [S3](/aws/storage/s3/) |
| Managed specialised filesystem | [FSx](/aws/storage/fsx-hpc/) |

S3 is object storage, not a POSIX filesystem. A tool that presents objects through a mount does not automatically provide
the atomic rename, locking, metadata, latency, or consistency behaviour expected from a local filesystem.

## Operational checklist

For a failed write, check identity and path traversal, read-only or restrictive mount options, free blocks, free inodes,
quotas, filesystem errors, and deleted-but-open files. For a slow path, separate application I/O, local device latency,
network filesystem latency, and downstream storage throttling.
