Linux discretionary access control evaluates a process's credentials against file ownership, mode bits, and optional ACLs.
The basic mode has read, write, and execute bits for the owner, group, and others.

~~~bash
ls -l /path/to/file
stat /path/to/file
namei -l /path/to/file
getfacl /path/to/file
~~~

Directory permissions have special meaning: read lists names, write changes directory entries, and execute traverses or
searches the directory.

## Numeric and symbolic modes

Read, write, and execute correspond to 4, 2, and 1:

~~~bash
chmod 640 config
chmod u=rw,g=r,o= config
chmod 750 script
~~~

Changing mode does not change owner or group; use <code>chown</code> and <code>chgrp</code> for those operations.

## setuid on executable files

When an eligible executable has setuid, the new process receives an effective user ID based on the file owner. This can
grant narrowly scoped privileged behaviour, but a flaw in the executable may become a privilege-escalation path.

The bit appears as <code>s</code> in the owner's execute position:

~~~text
-rwsr-xr-x
~~~

Scripts generally should not rely on setuid semantics. Prefer a small, reviewed executable, a service boundary, or a
specific capability when that accurately represents the required privilege.

## setgid

On an executable, setgid changes the effective group according to the file's group. On a directory, it commonly causes
new children to inherit the directory's group, which is useful for collaborative directories:

~~~bash
chgrp engineering /srv/shared
chmod 2770 /srv/shared
~~~

An appropriate umask or default ACL is still needed to control the permissions of newly created files.

## Sticky directories

The sticky bit on a writable directory restricts removal or renaming so users cannot normally remove entries owned by
other users merely because the directory is writable. <code>/tmp</code> is the familiar example:

~~~text
drwxrwxrwt
~~~

Set it with <code>chmod 1777 DIRECTORY</code> only when that shared-write model is intended.

## Mounts and capabilities

Mount options can further restrict execution:

- <code>nosuid</code> ignores setuid and setgid effects;
- <code>noexec</code> restricts direct execution from the mount;
- <code>nodev</code> prevents device-file interpretation.

Linux capabilities divide traditional root privilege into smaller units. Granting only the required capability can be
safer than full setuid-root, but capabilities remain powerful and need review.

## Review checklist

- Which process identity needs the access?
- Is group ownership or an ACL sufficient?
- Can the privileged operation live behind a service API?
- Do container, systemd, or mount restrictions change the result?
- Is the effective permission visible in tests and deployment checks?
- Are world-writable and setuid/setgid files monitored?
