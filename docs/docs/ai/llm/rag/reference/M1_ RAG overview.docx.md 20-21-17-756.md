## RAG applications

As you just saw, the core idea of RAG is to pair an off-the-shelf LLM with a knowledge base of information it might not have had access to when it was trained. Many LLM-powered systems implement this model, so let's explore a few of them now. One important application of RAG is for code generation. This is significant because while language models have been trained on lots of code, conceivably every public Git repository, generating correct code for a specific project requires specialized information. The LLM needs to know the classes, functions, and definitions in the project, as well as the overall coding style being used. Building a RAG system that uses your own code base as the knowledge base makes this information available to an LLM. By retrieving relevant classes, definitions, and files from your repository, an LLM is much better able to generate code or answer questions relevant to your project.   
Another major application is customizing chatbots to an individual company. Every company has its own products, policies, and communication guidelines. Treating these enterprise documents as a knowledge base allows you to deploy LLMs in a variety of useful ways. You could build a customer service chatbot that knows information about your company's product, current inventory, or common troubleshooting steps. You could deploy an internal chatbot that accurately answers questions about company policies or directs you towards useful documentation. In either case, the knowledge base helps ground the LLM's responses in your company's specific products or policies, and helps minimize instances where the LLM generates generic or misleading responses. RAG has significant applications in healthcare and legal domains.   
In these instances, the knowledge base might contain legal documents from a particular case, text from recently published medical journals, and so forth. In fields like these, in which precision is imperative and the amount of niche and potentially private information is vast, a RAG-based approach might be the only way to deploy an LLM-based product that is sufficiently accurate and uses private information. Another major application is an AI-assisted web search. Historically, search engines have worked like a retriever. Given a search query, they return relevant websites. Today, search engines will provide AI summaries of these search results to quickly present the most useful information in a skimmable way. These AI web summaries are basically a RAG system whose knowledge base is the entire internet.   
While large-scale RAG systems can be powerful, the same is true for highly personalized ones. Personalized assistants in your text messages, email client, word processor, calendar, and so forth are now able to help you send messages, organize your schedule, draft documents, and complete projects big and small. In each case, the more context the LLM has about the project you're working on, the better they're able to support that work. In these cases, the knowledge base might be relatively small. For example, your text messages, contact lists, emails, or a folder of documents. These kinds of documents are dense with important context. So a RAG system with access to this small-scale personal information can complete tasks in a way that is significantly more relevant to what you're doing.   
As you can see, the RAG model has applicability in a wide variety of contexts. Many companies, organizations, and even you have collections of information that could be used to enhance the quality of text generated by an LLM. Whenever you have access to information that likely wasn't used to train a large-language model, there is a potential for building a useful RAG application. They might even allow LLMs to be used in contexts that were otherwise impossible. ## RAG architecture

You've already seen the most important components in a RAG system, namely the LLM itself, a knowledge base of relevant information, and a retriever that can search the knowledge base. Now let's look at the overall architecture of a RAG system and how these components work together. Let's start by looking at how you normally use a large language model. You type a prompt and send it to the LLM. The LLM processes the prompt and generates a response. The user experience for a RAG system is actually identical. You submit a prompt and get back a response. Inside the system, however, there's a few more steps. When the RAG system receives your prompt, it first routes it to the retriever. The retriever has access to the knowledge base, which practically speaking is just a database of useful documents. The retriever queries the database, returning documents that it determines are most relevant to the prompt. Next, the system creates an augmented prompt, incorporating information from the relevant documents into the original prompt. For example, an augmented prompt might be, answer the following question, why are hotels in Vancouver so expensive this coming weekend? Here are five relevant articles that may help you respond, and then insert text from the articles. At this point, the system operates like any other LLM. The augmented prompt is sent to the LLM and it generates a response.   
The LLM is able to respond based on both the knowledge it learned from its training data, as well as any additional context provided by the retrieved documents. The user experience is the same as always, perhaps with a little bit of added latency. You type a prompt and you get back a response. Thanks to that side route through the retriever, however, there's a higher likelihood the response is accurate, up-to-date, and context aware. As you just saw, the main difference between using an LLM directly and a RAG system is the addition of the retriever. This fairly straightforward addition, however, allows for a number of advantages. First and most importantly, it makes information available to the LLM that might otherwise not be. Whether it's company policies, a piece of personal information, or this morning's headlines, RAG is often the only way to make some kinds of information available to an LLM. Related to this first point, RAG reduces the likelihood of hallucinations or misleading responses. These are often caused by LLMs generating responses about topics which were excluded from their training data or perhaps just mentioned rarely. Adding relevant information directly in the prompt grounds the language model's responses and makes them less likely to create generic or misleading text. RAG makes it much easier to keep LLMs up-to-date with rapidly changing information. Retraining a language model is usually a costly and time-consuming feat, so LLMs struggle to keep up with very new information. In a RAG system, however, you can simply update the information in the knowledge base just like you'd update entries in any other database. As soon as those changes are indexed, your LLM will be able to respond based on the new information. RAG improves an LLM's ability to cite sources. A RAG system can add citation information to the augmented prompt and the LLM can then include that information in its ultimate response.   
This doesn't just ground the response but enables human readers to dig deeper and validate the generated text. Finally, RAG allows an LLM to focus on this text generation. The retriever filters down a vast world of information, finds what's most important and relevant, and presents it succinctly. The LLM still needs to write a good response, but it's not being relied upon to do fact-finding or filtering steps. In other words, each component is assigned to work on the area of its greatest strength.

## How LLM works

[https://www.coursera.org/learn/retrieval-augmented-generation-rag/lecture/hlhBO/introduction-to-llms](https://www.coursera.org/learn/retrieval-augmented-generation-rag/lecture/hlhBO/introduction-to-llms)  
Technically, an LLM doesn't generate words, but rather tokens, which is a more generic term for pieces of words. Some words like London and door might have their own token, but common compound words like programmatically and unhappy are usually split into multiple tokens.   
Punctuation, like the period, comma, and the question mark could also get their own tokens. Most LLMs have a total vocabulary of anywhere from 10 to more than 100,000 tokens. Having the flexibility to build up compound words out of smaller word pieces, allows the model to build any possible word without needing to actually assign a token to each one.

For example, after choosing shining, the LLM might choose in, the, and sky since those words all make sense in the context of the words chosen before them. If that initial generated token had been warming, however, the LLM might then choose our faces as that makes more sense given the direction the LLM took the completion. This behavior is called autoregressive, meaning self-influencing. Thanks to the randomness and autoregressive nature, running the same prompt multiple times through the same LLM will usually lead to different completions.

### Hallucinations

Let's start with hallucinations. All LLMs can do is generate probable sequences of words based on the patterns they learned in their training data. If you ask an LLM about your company's private, internal data or today's news, the model almost certainly wasn't trained on that information and so isn't in a good position to respond. In these instances, an LLM will sometimes give responses that sound right, but aren't actually true. Even though these behaviors are called hallucinations, it's important to remember the LLM isn't having a psychological episode or even really malfunctioning. LLMs are designed to generate probable text, not truthful text. Truth, as far as an LLM is concerned, is just that a sequence of words is probabilistically likely based on its training data.   
With high quality training data, our intuitive understanding of truth and an LLM's mathematical understanding of probable word sequences can be kept in alignment. The challenge then is to ensure the LLM has access to as much relevant information as possible.

## Introduction to information retrieval

A well-designed retriever should of course return relevant documents but it also needs to withhold irrelevant documents. If you ask for information about making New York style pizza at home and the retriever responded with all the documents in the knowledge base, technically you'd have every relevant document but it'd be lost in a mountain of irrelevant information. As you saw earlier, this would also lead to costly prompts or even entirely use up the LLM's context window. On the other hand, if you only retrieve the highest ranked documents in the knowledge base, you might miss valuable relevant information in the documents ranked second, third, or fourth. In a perfect world, the retriever perfectly ranks the documents and chooses the exact right number of them to return. In practice however, you know the retriever will sometimes rank some relevant documents too low and rank some other irrelevant documents too high, making it difficult to confidently decide how many of them to return. To optimize a retriever's performance, you'll need to monitor it over time and experiment with different settings, something you'll see extensively in this course.

Retrieval Augmented Generation is hopefully already starting to feel more approachable. Its goal is to make LLMs more useful and more accurate by giving them access to information that they might not have had when being trained. In order to do this, the LLM is paired with a collection of data called the Knowledge Base. This data might be private, recent, or just highly specific, and so not included in an off-the-shelf LLM's training data. When users submit prompts, they're first routed to the Retriever. The Retriever searches the Knowledge Base for relevant documents and adds text from those documents to the user prompts. LLMs are able to incorporate this information from the prompts into the responses they generate.   
The retrieved information grounds the final response, making it more accurate and relevant.
